---
topic: Labels on issues
goal: let teams group and filter issues across statuses
updated: 2026-10-21T09:01
---

- (direction) request: add labels to issues so a team can tag bugs, features and areas, and find them again
- (note) mode: guided; input is a one-line request plus the existing codebase (projects, issues, list and board views)
- (decision) labels belong to one project; a project's labels are not visible in other projects (projects already scope issue numbers and keys)
- (decision) label name is 1-30 characters, unique per project ignoring case, so "Bug" and "bug" cannot both exist
- (decision) label color is picked from a fixed palette of 8 colors, so chips stay readable on the light UI
- (capability) CAP-1 a person can create a label in a project with a name and a palette color
- (capability) CAP-2 a person can set the labels of an issue (add and remove) from the issue panel
- (capability) CAP-3 labels show on every issue in the list view and on the board cards
- (capability) CAP-4 a person can filter the issues of a project by one label in both views
- (decision) an issue has at most 5 labels; a 6th is rejected with a 400 so the list stays scannable
- (decision) setting labels replaces the whole set in one request (PUT with labelIds), so the UI never has to diff
- (constraint) a label from another project cannot be put on an issue; the API answers 400
- (constraint) issue responses include their labels sorted by name, so the web app needs no second request
- (constraint) follow the existing layers, error format and UTC dates from AGENTS.md
- (decision) non-goal: renaming, recoloring or deleting labels; deferred to keep the first slice small
- (decision) non-goal: labels shared across projects, label groups, label descriptions
- (decision) non-goal: filtering by more than one label at a time
- (note) success signal: on WEB, create "bug", put it on two issues, filter the board by it and see exactly those two issues
- (decision) story split: story 1 data model and API; story 2 web app. API first so the UI story builds on a stable contract
- (event) self-validate pass 1 coherence: 4 capabilities, each with intent and success; 3 non-goals; constraints all rule something out
- (event) self-validate pass 2 preservation: every load-bearing claim of the request is in SPEC.md
- (event) story breakdown check: stories.yaml has 2 entries, ids "1" and "2", quoted, prefix-free, no status field
- (event) spec finalized
